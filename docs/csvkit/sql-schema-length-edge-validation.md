# SQL schema length multiplication regression

The current user review validated one source mismatch before editing code: connected MySQL text lengths were multiplied as exact BigInts, but agate-sql 0.7.3 uses `Decimal(multiplier)` under precision 28 and half-even rounding. Large negative multipliers paired with negative minimum lengths expose the difference without triggering the positive TEXT threshold. The target remains csvkit 2.2.0 source archive SHA-256 `147318a8dbaec07c0bbb9291c14b78de5fa32ed3d4a5c2396e52a83c0a30df6b`.

Research used the existing reference at out/csvkit-rounding-reference/bin/python. Its executable SHA-256 was rechecked as `3d6400b63b150164e89a690d9813af8b0eb420af9f336ef1f6c5102c6da60eae`, matching reference-profile.json; observed versions were CPython 3.14.2, csvkit 2.2.0, Agate 1.14.2, agate-sql 0.7.3 and SQLAlchemy 2.0.54. This focused recheck does not claim a fresh complete distribution/archive authentication.

For text `abc`, multiplier `-123456789012345678901234567890123` and minimum `-10000000000000000000000000000000000000000`, the native raw CREATE uses `VARCHAR(-370370367037037036703703703700000)`. The original engine emitted `VARCHAR(-370370367037037036703703703670369)`. The in-memory regression in csvsql.test.ts failed with those exact bytes before the source change. Two additional halfway products independently measured native half-even behavior. Derivation now uses the existing Decimal arithmetic implementation before threshold/minimum comparisons; compiler/provider registration and schema-only option forwarding are unchanged.
