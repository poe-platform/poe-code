# SQLite binding independent stress validation

The independently authored actual-Shell suite is `packages/safe-bash/tests/commands/csvkit-sqlite-binding-stress.test.ts`. Its loader reads the existing pinned SQLite WASM infrastructure asset; its command invocations use only initialized, injected SQLite and MemoryFileSystem capabilities. The procedure is `docs/plans/csvkit-sqlite-binding-stress-qa.md`.

The initial uncached run failed before case execution because `@poe-code/csvkit` did not expose `createSqliteDatabaseProvider`. This was red implementation evidence; no SQL case ran.

After the maintained csvkit build, the suite ran fifteen cases: fourteen passed and `PRAGMA encoding` failed with status 0 and empty stdout rather than `encoding\nUTF-8\n`. The engine captured column metadata before the first SQLite step; root moved capture after stepping. That change did not resolve the encoding mismatch.

Two independent real-engine lifecycle cases were then added. Actual Shell cancellation while an already-acquired SQLite session was held behind a cooperative promise remained pending until release, then rolled back and closed the real session once. Output consumer closure finalized the real SQLite statement/result/session once and preserved the root caller signal. The latest uncached command `node --import tsx --test packages/safe-bash/tests/commands/csvkit-sqlite-binding-stress.test.ts` ran seventeen cases: sixteen passed, one failed, with no skips or TODOs.

A direct pinned-WASM probe confirmed the unresolved failure is an engine-build omission: `PRAGMA encoding` returned no columns/rows, and `PRAGMA compile_options` included `OMIT_UTF16`. Other observed omissions were `MUTEX_OMIT`, `OMIT_DEPRECATED`, `OMIT_LOAD_EXTENSION` and `OMIT_SHARED_CACHE`. The original reference behavior remains a compatibility blocker. A named rejection can qualify safe refusal; it cannot turn this missing SQLite capability into a parity pass.

The declared result coverage includes the frozen SQLite version, recursive CTE, aggregate, join, window function, ordered output, subquery, NULL, signed 64-bit integer, integral/fractional floating-point representation, date functions, blob representation, collation, and semicolons inside string literals. csvsql imports into the same engine. The four capability-denial cases cover ATTACH, VACUUM INTO, load_extension and unbound file URLs; each asserts status 78, no stdout and unchanged authorized MemoryFileSystem entries. Every owned provider is explicitly disposed in finally.

These focused cases do not qualify arbitrary queries, the complete PRAGMA/function/compile-option surface, malformed UTF-8 TEXT diagnostics, all SQLAlchemy error/parameter formatting, synchronous same-thread query preemption, SQLite mutex/shared-cache behavior, total WASM memory accounting, or filesystem crash atomicity. File-backed VFS qualification is owned by root integration and is not established by this in-memory suite.

The canonical suite now separates the absent `PRAGMA encoding` reference case into a named fail-closed host-divergence assertion. Supported result expectations comprise nine sql2csv cases and one csvsql import/query case. Five denial cases and two lifecycle cases assess refusal/cleanup rather than reference SQL compatibility. The original encoding discrepancy above remains a parity blocker, regardless of whether the denial assertion subsequently passes. Root independently revalidated the frozen CPython 3.14.2 executable hash and SQLite 3.50.4 reference and captured its UTF-8 encoding result.

After root's named encoding divergence and maintained csvkit rebuild, the final uncached focused command completed with seventeen passing behavioral assertions, zero failures, zero skips and zero TODOs. Ten assertions compare supported result bytes/status; seven assess host refusal or lifecycle. In particular, the passing encoding assertion verifies status 78 and a named `SQLite host divergence` diagnostic. It does not verify reference encoding output or resolve `OMIT_UTF16` compatibility.

After root first reproduced and fixed the direct-provider invocation-cwd regression, the independent suite added an actual-Shell relative-file-URL case using exported `createMemorySqliteFileSystem` and a memfs Volume. The provider fallback cwd is `/`, the Shell cwd is `/authorized/sub`, and both virtual namespaces explicitly contain the authorized parent directory. `csvsql --db sqlite:///rows.db --insert` commits rows; a fresh `sql2csv` session reopens the same URL and outputs exactly `a\nx\ny\n`. The test verifies `/authorized/sub/rows.db` exists and is nonempty, `/rows.db` does not exist, and the transaction journal is removed. This measures in-process memfs persistence and command-cwd propagation, with no disk durability/atomicity claim.

The unchanged seventeen-case baseline passed before this addition; the expanded focused command passed eighteen assertions with zero failures/skips/TODOs. Classification is eleven supported result/workflow assertions and seven safety/lifecycle assertions. The `OMIT_UTF16` blocker remains unresolved.
