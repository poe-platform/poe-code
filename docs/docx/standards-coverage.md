# DOCX standards coverage research

Status: Standards sources and schema declarations reviewed; product behavior not implemented.

Research date: 2026-09-13. Baseline: `dbf33f6554bbd31fe7f696b35cc51910fdfcf198`.

The authoritative target remains [the proposed DOCX specification](../specs/docx.md).
This register maps all 50 families to actual publisher sections and schema declarations,
intended support boundaries and [original acceptance cases](../plans/docx-standards-audit.md).
A row is research coverage, **not a passing product test**. Every behavioral case below is
pending implementation. This is neither complete schema implementation nor ISO certification.

## Namespace and schema key

Prefixes are labels for expanded names, not required serialized prefixes. P1 schema
names below identify Strict declarations; P4 supplies the Transitional counterparts.
The same local type name does not imply identical content models or attribute types.
OPC namespaces remain unchanged between document dialects. `wT` explicitly denotes the
P4 WML schema where a declaration exists only there. Schema witnesses identify the
actual declaration consulted, not an assertion that all its children are editable.

(§2.7), `http://schemas.microsoft.com/office/word/2018/wordml` (§2.9),
`http://schemas.microsoft.com/office/word/2020/wordml/sdtdatahash` (§2.11),
`http://schemas.microsoft.com/office/word/2023/wordml/word16du` (§2.12) and
`http://schemas.microsoft.com/office/word/2024/wordml/sdtformatlock` (§2.13).
They are inventory/preserve targets, not general editing support. Operations affecting
checksums, locks or annotation dates require verified interpretation or rejection;
ignorable does not mean safe to mutate. Other ODRAW extensions, including new chart
families, 3D, ink, script links and live feeds, remain opaque and inert. No unpinned
Office-extension schema is implicitly understood. XMLDSig, SVG syntax, image encodings
and embedded binary formats are separate standards boundaries; container/schema
recognition alone cannot certify those payloads.

## F01–F50 coverage register

Each row records the proposed **read / edit / preserve / reject** boundary. “Preserve”
means exact unmodified opaque-part payload retention plus retained relationship edges;
for edited XML parts it means retaining unrelated subtrees, namespace bindings, order
and meaningful whitespace as required by F04. Recompression need not reproduce ZIP bytes.
“Reject” identifies unsupported operations or inadmissible input; it does not require
rejecting an otherwise safe document merely because it contains an opaque object.
All edits also obey limits, protection, signatures, stale selectors and atomic publication.

Product-level algorithms such as selection, dummy text, diff and batch have no OOXML
schema type of their own. Their rows deliberately cite the structures they read/change
and the product contract, rather than inventing normative ECMA algorithms.

## Processing distinctions from the actual sources

P2 §6.5.3.1 requires Relationships XML to be schema-valid after MCE processing with
an application configuration containing only the Relationships namespace; it prohibits
`xml:base` in that output. The WML understood profile must not leak into OPC relationship
processing. P2 §6.2.2 names parts with IRI rules; host filesystem naming is a separate
publication constraint. P2 §7.2 describes interleaved pieces, which are not covered by
the proposed ordinary ZIP-entry writer; report that limitation instead of silently
concatenating pieces or claiming complete OPC support.

P3 §9 defines a semantic processed document. It removes ignored markup and unwraps
selected content. F04/F05 additionally require a retained original representation for
editing and preservation: serializing only the processed view would lose required
unselected branches. Unknown `MustUnderstand` namespaces signal a mismatch where the
processing model examines them; do not globally reject attributes in branches that
P3 says are ignored. An affected fallback/alternate representation that cannot be
updated consistently needs an unsupported-edit result. P3 §§7–9, rather than an
invented XSD type or SDK guidance, govern this decision.

P1 §17.13.2 pairs annotation endpoints by ID even when ranges cross structural
boundaries. XML tree nesting alone cannot validate bookmarks/comments/moves. P1 §17.12
also gives glossary content its own relationships, styles and numbering context.
Part-local and story-local IDs must remain distinct from public selection tokens.
P1 §17.6 describes section/page formatting rather than stored measured pages; cached
page breaks, TOCs and page numbers cannot prove rendering fidelity.

### Confirmed documentation drift

The [API audit](upstream-api-audit.md) and [331-record candidate inventory](upstream-api-inventory.json)
were read. The source revision remains `e45454602b53e8e572b179ccf1c91093ec9f4ed7`.
The candidate count is not an exhaustive public API denominator. No inventory row is
marked implemented, and no public API is excluded because its name starts with `_`.

1. The pinned guide `docs/user/comments.rst` lines 99/105 uses `id`/`date`, whereas
   `src/docx/comments.py` exposes `comment_id` (line 130) and `timestamp` (line 158).
   Resolve these guide errors to `comment_id: number` and `timestamp: Date | null`
   (read-only). Do not add accidental `id`/`date` aliases. Missing `Comments.get(id)`
   returns `null`. Rich comment content and anchor restrictions remain required.
2. `src/docx/document.py` lines 128–135 and `src/docx/image/image.py` lines 86–100,
   116–160 define native dimensions from embedded DPI with a **72-DPI fallback**.
   The prior format-spec sentence prescribed 96 DPI without distinguishing contexts.
   The spec now reserves **96 DPI for explicit generic pixel-to-EMU conversion**;
   native picture sizing uses admitted image DPI with the documented 72 fallback.
   Neither rule comes from ECMA. One supplied dimension preserves aspect ratio;
   both supplied dimensions are explicit. The same default behavior must hold for
   the matching SDK and CLI image operation. Invalid metadata is not an excuse to
   skip bounded format admission; per-format details remain a later API task.
3. Python integer subclass truncation differs from the shared Office rounding
   contract. The mapping above deliberately uses safe value objects and shared
   nearest/half-away rounding; test fractional and negative half cases explicitly.
   This is a language mapping, not literal Python runtime compatibility.

No source test bodies, document passages, artwork or binary fixtures were copied.
The test obligations are original contract-based cases. Existing research/legal notices
remain separate. Complete adaptation of the 2,259 collected behavioral variants and
complete public member mapping are later tasks; this standards audit claims neither.
