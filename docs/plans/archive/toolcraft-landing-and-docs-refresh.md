# Toolcraft landing and documentation refresh

## 1. What we're improving

Refresh the generated Toolcraft family landing page so a new visitor can answer four questions without scrolling through a feature inventory:

1. What is Toolcraft?
2. Why is it different from another CLI or MCP framework?
3. Can I see the core idea in working code?
4. Where do I start for my task?

The page remains a self-contained static HTML document generated by `toolcraft-landing-page`. No framework, external font, analytics, image dependency, or network request is added.

## 2. Reference research

The redesign borrows recurring information-design patterns rather than copying any site's visual identity:

- **Zod**: an extremely short value proposition, install command above the fold, and immediate documentation path.
- **Hono**: outcome-led positioning and a compact list of concrete reasons to choose the library.
- **Vitest**: a runnable code example near the top and ecosystem capabilities presented as proof, not slogans.
- **Vite**: clear primary and secondary calls to action plus progressive disclosure from overview to guide.
- **React docs**: task-oriented learning paths and examples that explain a mental model before API detail.
- **Playwright docs**: direct install/get-started flow, copyable commands, and navigation organized around user jobs.
- **Tailwind CSS docs**: persistent documentation navigation and scannable, code-led explanations.
- **Astro docs**: newcomer routes, recipes, and strong separation between learning and reference material.

## 3. Landing-page changes

- Add two explicit hero actions: `Get started` and `View on GitHub`.
- Add a compact trust row stating the architectural guarantees: typed, one handler, zero runtime web dependencies, and Node support.
- Move the worked example ahead of broad use cases so visitors see the defining mechanism earlier.
- Add a three-step `How it works` section: define, expose, govern.
- Replace generic documentation discovery with task-oriented cards for first command, runtime surfaces, safety, and migration.
- Finish with a focused call-to-action that repeats install and documentation entry points.
- Preserve accessibility, dark mode, reduced motion, print output, and mobile overflow behavior.

## 4. Documentation changes

Create a dedicated `packages/toolcraft-landing-page/docs/index.md` entry page. It is concise and task-first:

- a five-minute first command;
- a mental model for command trees and generated surfaces;
- links to the authoritative package guides for schemas, OpenAPI generation, and code mode;
- recipes for scripts, MCP tools, approvals, and SDK usage;
- explicit environment and configuration statements.

The package README remains package-specific and links to this guide. The root README is not changed without explicit permission.

## 5. Verification

- Unit tests assert the new semantic sections, links, and responsive behavior before implementation.
- The package build and unit suite pass.
- The generated static site remains deterministic and self-contained.
- Desktop and mobile screenshots verify hierarchy, overflow, dark/light compatibility, and usable calls to action.
