# Synchronous unhandled-rejection policy qualification

The frozen runner accounts for every observed unhandled Promise rejection as a nonpass. This is a conservative runner policy; it is not a rule that every unhandled rejection is an ECMAScript failure or an uncaught Script exception.

[ECMA-262 edition 16 §27.2.1.9, HostPromiseRejectionTracker](https://262.ecma-international.org/16.0/#sec-host-promise-rejection-tracker) defines a host hook returning `unused`; its default implementation also returns `unused`. The fresh document fetch matched the unchanged target SHA-256 `6a28f9423133ed7b7c59a40baf620c2740f12f0bc9c251042f2a85b9cc5ed713`. Pinned Test262 `INTERPRETING.md` lines 183–188 define ordinary outcomes in terms of uncaught exceptions and normal completion. Its async section and `CONTRIBUTING.md` lines 356–376 require the async flag and exactly one successful completion signal. Neither document mandates a blanket failure for every ignored Promise rejection.

The smallest pinned demonstration is `built-ins/Promise/all/invoke-resolve-error-close.js`: it replaces `Promise.resolve` with a throwing function, calls `Promise.all` without observing its returned rejected Promise, and checks only that the iterator was closed once. It has no async flag. The frozen baseline records both variants as `failed/unhandled-rejection`. This reason is produced after the synchronous outcome has already passed classification, so the rejection accounting cannot be treated as evidence that the iterator-close assertion failed.

The neighboring `invoke-resolve-error-reject.js` explicitly uses the async flag, checks the rejection through handlers and finishes with `.then($DONE, $DONE)`. Both variants pass in the same frozen baseline. Exact fixture hashes, original rows, contract references and the unchanged manifest ID are retained in [the contract receipt](sync-rejection-policy-contract.json).

Disposition: preserve the original nonpass counts. Categorize these rows under **runner/host-policy qualification**, owned by the Test262 runner's synchronous Promise-rejection result policy. Do not count them as ECMAScript defects, silently promote them to passing or mix results from a different runner revision. A follow-up can qualify when rejections should be informational versus failing, using fast regressions and the pinned synchronous/async pair before changing policy. The current full baseline is a complete measurement under its explicit conservative policy, not an exact count of normative incompatibilities. No runtime or frozen runner source changed during this review.
