## Source-backed behavior

Typed models load the retained native Gnumeric Solver representation (including MPS-generated native records), objective direction/target, rectangular variables and constraints, integer/binary domains, declared linear/quadratic/nonlinear type, iteration/time limits, nonnegative/discrete/scaling/report options, plus native constructor gradient/scenario defaults. Boolean parsing preserves the native false/zero semantics; valid signed iteration values preserve the unsigned storage bits. Constraint sides use numeric-first number matching before ranges, including ambiguous time/whole-row syntax. Classification is declared metadata, not an inferred mathematical proof. Native XML names are empty placeholders until delayed definitions install; retained solver named references therefore do not resolve from final-workbook names. Formula references inside objective cells and grouped array/shared expressions use the actual calculation engine; numeric group objectives validate and grouped input formulas are rejected. Active sheet is selected by id before falling back to the first sheet.

`run_solver` keeps a functional saved algorithm even when its type differs from the declared model. Otherwise it scans functional factories of matching model type; the native registry is sorted by casefolded display name. The JS registry uses explicit C-profile order GLPK (`glpk`), LPSolve (`lpsolve`), Nlsolve (`nlsolve`), all unavailable. Factory ids are the short manifest service ids, as confirmed in gnm-plugin.c. No host program/configuration/plugin discovery is performed. No quadratic factory exists in the released three manifests. XML does not serialize an algorithm choice; the internal selector supports an explicit saved id for selection tests. The public SDK exposes the snapshot-owning parameter loader; validation and selection run inside the existing shared engine boundary.

Validation checks target existence, numeric formula target, input range, formula input cells, then constraints in source order. Validation failures emit `Solver: <message>` and conversion proceeds as native run_solver does. Valid models without JS execution throw an unsupported-feature error/status 1 before publication. This deliberate parity blocker prevents successful no-op solving; native creation-failure/status behavior is not claimed for unavailable JS algorithms. Injected pre-existing SolverCapability remains the explicit execution boundary shared by SDK/CLI.

Native shared timeout cancels only when elapsed time exceeds MaxTime while running; equality does not cancel. The iterative solver increments iterations after invoking its iterator, completes when progress stops, otherwise cancels at iterations >= MaxIter. Cancelled solvers print `Solver reached time or iteration limit`, store a result and create the report. GLPK/LPSolve subprocess limits are plugin-specific, not universal iteration behavior. These execution details are audited only, not implemented or measured as numerical parity.

Source search found no spreadsheet solver import handler in the released Excel or OpenOffice importers. Excel Escher SolverContainer is drawing metadata, not spreadsheet optimizer parameters. Excel Solver add-in/private records and ODF vendor extension representations have no validated import mapping here and remain unmeasured; do not synthesize metadata or claim those cases pass. Existing codec retention is preserved.

## Remaining mismatches and unmeasured cases

GLPK, LPSolve and Nlsolve JS execution, quadratic optimization, numerical solutions, result storage/reports/scenarios/sensitivity, iteration/time-limit execution and native optional-solver availability are parity blockers. Product never calls native libraries/programs, even if an oracle has them.

Native input-cell allocation and target-evaluation/recalculation mutation ordering are not fully reproduced: validation currently evaluates a workbook snapshot and returns the original model workbook on a validation warning. Malformed/out-of-range XML integer coercion, localized constraint-number parsing, legacy invalid/zero dimensions, detached/3D/external solver references, spreadsheet-convention-specific diagnostics and arbitrary recalculation side effects remain unmeasured. No full solver parity claim follows from source audit or unit success. New native differential QA, including captured solver-specific optional dependency activation, is still required.
