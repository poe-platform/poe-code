# toolcraft-landing-page

A toolcraft surface that derives a single self-contained static HTML landing page from a command tree.

## 1. What we're building

A `toolcraft-landing-page` package. It takes a toolcraft command tree (a `root` group) and produces a static HTML landing page documenting the tool — the same "define once" model as CLI/MCP/SDK, now extended to a web page. It joins the `toolcraft-*` family (`toolcraft-schema`, `toolcraft-openapi`, `toolcraft-codemode`).

The page is a single self-contained `index.html`: inlined CSS, a small amount of inlined vanilla JS (copy-to-clipboard, smooth-scroll), no external assets, no framework, no animation library. Rendering goes through the existing `renderTemplate` Mustache engine in `toolcraft-design`.

Design language: minimal and typography-forward — system sans for prose, monospace for commands/code, generous whitespace, single centered column, hairline borders, and one restrained accent color (default `#a200ff`, the existing design-system brand token). Hero with the tool name/headline/install line, a "one definition → every surface" strip, then command reference cards grouped by sub-group, each with parameter tables and scope/approval/secret badges.

Non-goals:
- No bundler, SSG, or new toolchain (no Astro/Vite/Webpack).
- No multi-page output, no client-side routing, no search index.
- No animation library, no theming system beyond a single accent option.
- Not a marketing-copy authoring tool: prose beyond the configurable headline/tagline is derived from the tree, not hand-written per page.

## 2. User-facing shape

### SDK (primary surface)

```ts
import { renderLandingPage } from "toolcraft-landing-page";
import { writeFileSync } from "node:fs";
import { root } from "./root.js";

const html = renderLandingPage(root, {
  install: "npm install -g acme",
  version: "1.4.0",
  repoUrl: "https://github.com/acme/acme",
});

writeFileSync("index.html", html);
```

`renderLandingPage(root, options?)` returns a complete HTML document string. The caller owns I/O. Options mirror the CLI flags one-for-one (CLI/SDK parity).

### CLI

The bin is a toolcraft command (dogfooded), so it gets `--help`, kebab flags, and exit codes for free.

```
toolcraft-landing-page --root ./dist/root.js --out ./index.html

Options
  --root <path>       Module exporting the toolcraft root group (named `root` or default export). [required]
  --out <path>        Output file. [index.html]
  --title <string>    Page + document title. [root.name]
  --headline <string> Hero headline. ["Define a command once. Run it everywhere."]
  --tagline <string>  Hero sub-headline. [root.description]
  --install <string>  Install command shown in the hero. [omitted if unset]
  --version <string>  Version shown in the eyebrow and footer. [omitted if unset]
  --repo-url <url>    Repository link in the nav. [omitted if unset]
  --accent <color>    CSS accent color. [#a200ff]
  --no-js             Emit a zero-JavaScript page (no copy buttons).
```

Example:

```sh
toolcraft-landing-page --root ./dist/root.js --out ./site/index.html \
  --install "npm install -g acme" --version 1.4.0 \
  --repo-url https://github.com/acme/acme
```

### Generated output

The design reference is the committed mock at [examples/index.html](../../packages/toolcraft-landing-page/examples/index.html) (a fictional `acme` CLI). The generator reproduces this structure and styling from any tree:

- **Sticky nav** — tool name + anchor links (Surfaces, Commands, Quickstart, and the repo link when `repoUrl` is set).
- **Hero** — eyebrow (`name · version`), headline, tagline, install line with a copy button, and a `N surfaces · N commands · N groups` summary.
- **Surfaces strip** — one card per runtime present in the tree (CLI / MCP / SDK), each with a one-line code sample.
- **Commands** — one section per sub-group (`group.name` + `group.description`); each command is a card: dotted path (`acme deploy prod`, namespace dimmed + leaf accented), description, badges (`approval` when human-in-loop, then one `scope` pill per exposed runtime), a parameter table (name, type, required/optional, default, description), a secrets line (`ENV_VAR — description`), and a copyable example invocation.
- **Quickstart** — install + a representative CLI invocation + MCP + SDK snippet.
- **Footer** — `name · version · Node 20+` and a `generated by toolcraft-landing-page` line.

The page is XSS-safe: every value pulled from the tree (descriptions, param names, secret descriptions) is HTML-escaped; only the static template markup is raw.

## 3. Implementation details and technical decisions

### Architecture

All logic lives in the new package; nothing outside it changes (the root `packages/*` workspace glob and turbo pick it up automatically).

```
packages/toolcraft-landing-page/
  src/
    model.ts        # public + internal view-model types
    walk.ts         # buildPageModel: tree -> PageView (pure, no I/O)
    template.ts     # HTML template string (Mustache tags)
    styles.ts       # CSS string constant
    script.ts       # inlined vanilla JS string constant
    render.ts       # renderLandingPage: buildPageModel + renderTemplate
    load-root.ts    # loadRoot(path, importer) -> Group (injectable importer)
    bin/generate.ts # toolcraft command + runCLI entry
    index.ts        # public exports
  examples/index.html   # committed design reference (already present)
  README.md
  package.json
  tsconfig.json
```

Separation of concerns: `walk.ts` is the only place that knows the toolcraft tree shape; `template.ts`/`styles.ts`/`script.ts` are the only place that knows HTML; `render.ts` joins them. This keeps the design swappable without touching tree traversal and vice versa.

### Templating

`render.ts` calls `renderTemplate(TEMPLATE, view, { escape: "html" })` from `toolcraft-design`. With `escape: "html"`, literal template markup passes through untouched while every `{{value}}` is HTML-escaped — exactly the contract needed to emit HTML safely. Repeated structures (groups, commands, params, badges) use Mustache sections (`{{#groups}}…{{/groups}}`) rather than pre-built fragments, so triple-stache is avoided. CSS and JS are concatenated into the template inside `<style>`/`<script>`; the accent color is injected as a `--accent` custom property via a single `{{accent}}` tag. CSS uses single braces only, so it never collides with Mustache's `{{`/`}}`.

### Reading the tree

- Walk `root.children` recursively. Direct child commands of `root` render in an unlabeled lead group; sub-groups render as labeled sections. A command's path is the space-joined chain of ancestor group names plus its own name.
- Parameters come from `toJsonSchema(command.params)` (`toolcraft-schema`): iterate `properties`, mark `required`, read `type`/`enum`/`default`/`description`. Positional params (`command.positional`) render without a `--` prefix; the rest render as `--name`.
- **Effective scope and human-in-loop must match toolcraft's own inheritance rules** (scope/`humanInLoop` cascade from group to child unless overridden). Reuse a toolcraft resolver if one is exported; otherwise compute inheritance in `walk.ts` using the documented rules (child value wins, else nearest ancestor, else the per-command default `["cli","sdk"]`). This is verified against toolcraft in the autonomy checklist — do not silently diverge.
- The surfaces strip lists only runtimes that appear on at least one command's effective scope.

### Edge cases

- Command/group with no description → omit the description line, no placeholder text.
- Command with no params → omit the parameter table.
- Command with no secrets → omit the secrets line.
- Empty group (no visible children) → skipped.
- `install`/`version`/`repoUrl` unset → those blocks/links are omitted (no guessed values — explicit over implicit).
- Enum param → type cell shows the enum values.
- Reserved `approvals` group that toolcraft auto-merges → excluded from the rendered reference (it is framework plumbing, not the tool's own surface).

### Config / env

- Config: the `LandingPageOptions` fields above. Defaults are stated literally in the README, not derived from naming.
- Default-on: `includeJs` is on (`--no-js` turns it off).
- Env vars: none. (The README still documents this explicitly.)

## 4. Interfaces and test plan

### Module-boundary types (`model.ts`)

```ts
export interface LandingPageOptions {
  title?: string;
  headline?: string;
  tagline?: string;
  install?: string;
  version?: string;
  repoUrl?: string;
  accent?: string;     // default "#a200ff"
  includeJs?: boolean; // default true
}

export interface ParamView {
  name: string;        // "--limit" or positional "target"
  type: string;        // "string" | "number" | "boolean" | enum rendering
  required: boolean;
  default?: string;
  description?: string;
}

export interface SecretView { env: string; description?: string; optional: boolean; }

export interface CommandView {
  path: string;        // "acme deploy prod"
  namespace: string;   // "acme deploy "
  leaf: string;        // "prod"
  description?: string;
  scopes: Array<"cli" | "mcp" | "sdk">;
  approval: boolean;
  params: ParamView[];
  secrets: SecretView[];
  example: string;     // copyable invocation
}

export interface GroupView { name?: string; description?: string; commands: CommandView[]; }

export interface PageView {
  title: string;
  headline: string;
  tagline?: string;
  install?: string;
  version?: string;
  repoUrl?: string;
  accent: string;
  includeJs: boolean;
  surfaces: Array<"cli" | "mcp" | "sdk">;
  surfaceCount: number;
  commandCount: number;
  groupCount: number;
  groups: GroupView[];
}
```

### Tests (TDD — write first, all fast, no real disk, no LLM)

- **`walk.test.ts`** — build a real fixture tree with `defineGroup`/`defineCommand`: a sub-group with two commands, mixed scopes, an inherited group scope, a human-in-loop command, a required secret, and params covering required/optional/default/positional/enum. Asserts every `PageView` field: counts, group/command paths, namespace/leaf split, effective scopes, approval flag, secret rows, param rows, derived example string, derived `surfaces`. Proves the tree→model mapping including inheritance.
- **`render.test.ts`** — asserts: output starts with `<!doctype html`; self-contained (`<style` present, no `<link ` and no `<script src=`); `--no-js`/`includeJs:false` emits no `<script`; a command description of `<script>alert(1)</script>` appears escaped, never raw (XSS); the `accent` value appears in the inlined CSS; `repoUrl`/`install` present vs absent toggles the nav link / hero block. Proves safe, self-contained HTML and option handling.
- **`load-root.test.ts`** — injects a fake `importer`; resolves `root`/default export; a module without a group throws a `UserError`. Proves dynamic loading without touching disk.
- **`bin/generate.test.ts`** — runs the generate command through the SDK with an injected `fs` service (memfs-backed) and injected importer; asserts the file is written with expected content and that a missing `--root` exits non-zero. Uses the repo's memfs idiom (`Volume.fromJSON` + `createFsFromVolume`). Proves the bin wiring.
- **Snapshot (`render.snapshot.test.ts`)** — render the committed `acme` example tree and snapshot the HTML to disk (on-disk snapshots are the allowed exception). Locks the generated structure against regressions and keeps it aligned with `examples/index.html`. Note: the hand-authored mock is the *design reference*; the snapshot is the *generated golden* — they share structure, not byte-for-byte marketing prose.

### Rollout / migration

New package, no existing callers — nothing to migrate. Published unscoped as `toolcraft-landing-page` (matching `toolcraft`, `toolcraft-schema`, `toolcraft-openapi`). Trusted-publishing/OIDC setup on npmjs.org for the new package name is required before first release.

### Visual QA

The repo's screenshot tooling is terminal-only, so HTML visual QA is a markdown QA doc: render the example tree (or open `examples/index.html`) in a browser and check hero, surfaces strip, command cards, badges, copy buttons, and mobile width. Headless Chrome (`--headless=new --screenshot`) is available locally for ad-hoc capture but is not wired into the package build.
