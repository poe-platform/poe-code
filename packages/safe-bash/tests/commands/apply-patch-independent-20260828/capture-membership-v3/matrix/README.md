## How to interpret fixtures

`utf8` is exact Unicode scalar text, `hex` exact binary bytes. `concat` and finite
`repeat` encode exact larger inputs without allocating or committing many MiB.
Lone surrogate argv uses explicit UTF16 code units and must not be preencoded.
JSON text is not code. Parameterized paths/counters use the explicitly described
finite substitutions only; no eval or hidden random generator is permitted.

Each case starts fresh with writable virtual `/work`, unless overridden, and an
unchanged binary `/sentinel`. Files maps are exact for declared fixture files;
absent targets are not implicit preserved files. Unspecified entries and unrelated
metadata remain untouched except disclosed provider defaults/read observations.
Directory defaults are `/` and `/work`; declared created directories remain after
partial failure. Provider metadata must be valid and stable unless a schedule
changes it. Shared scope/reason references denote actual same host objects, not
independently JSON-deserialized lookalikes. Unknown identity stays unknown.

An injected event occurs immediately before a specified call's effect or after
its fulfillment, as indicated. Faults specify exact partial bytes; external actor
and adapter-housekeeping effects are not command publications. No real provider
or package needs staging to interpret this data. Future actual Shell rows must
use actual dispatch, middleware and shared budgets, not callback-only substitutes.
Direct-handler rejection identity and public runtime status mapping are separate.

Success stdout is literal and specified by the pinned profile. Failure stdout is
empty unless an explicitly scheduled sink failure accepts a prefix. Failure
diagnostics bind status, UTF8 bound, prefix/newline, error/path meaning, and partial
publication qualification; exact bodies require **later diagnostic source review**.
Do not turn unexpected rejection values into invented byte-for-byte diagnostics.
