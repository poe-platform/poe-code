BOTTOM LINE
The original GNU9.7 difference is real and must remain a difference. It is
not safely fixed by preferring empty captures, nor by rejecting the pattern
and calling that native parity. There are two distinct observations:
1. The product's program-counter-only epsilon-cycle guard prunes legitimate
   repeated captures, including a longer overall match. This is a real engine
   issue even where expr's returned first-capture bytes hide it.
2. The pinned GNU9.7 implementation itself reports a partially open capture
   register for the original aaa case. Its empty expr result is not evidence
   that POSIX requires a terminal empty repetition to replace a nonempty one.
   A POSIX-correct repeat fix and exact GNU9.7 bug compatibility are different
   deliverables. No safe small GNU-profile parity patch was established here.

MINIMAL PROPOSAL FOR AUTHOR, NOT AN IMPLEMENTED/PASSING PATCH
Keep changes confined to bre-worker.ts if undertaking the semantic fix:
1. Preserve repeat identity and iteration entry offset in the lowering/executor,
   plus branch-local capture snapshot and required/optional iteration count.
   Backtracking must restore these frames together with captures.
2. Admit a new productive iteration even when it revisits a program counter at
   the current offset with different capture history. A loop-local progress
   boundary or capture/frame-aware epsilon state is necessary; pc alone is not.
3. On zero-progress repeat completion, exit that repeat rather than killing the
   whole continuation or blindly looping. Permit the initial sole empty match
   and enough mandatory empty iterations to meet the minimum. Do not overwrite
   prior productive captures with an additional gratuitous optional empty
   iteration; restore affected nested capture slots when abandoning it.
4. Keep completed, empty, and nonparticipating captures distinct. Choose maximal
   overall extent first, then correct capture-history precedence among valid
   paths. Merely changing first-accept/last-accept tie preference is insufficient.
5. Charge frame/capture copies and comparisons to Work allocation/steps/states;
   maintain existing cancellation/worker protocol/limits. Never clear visited
   indiscriminately or remove loop protection.
This is the minimum structural direction for this cause, not a claim that a
fully general POSIX submatch-ordering algorithm was implemented or verified.
It should produce aaa length 3/capture a; it will NOT reproduce GNU9.7's
unfinished first capture. Exact GNU9.7 parity would need separately specified
and narrowly qualified compatibility behavior, not a hardcoded odd-length rule.
I cannot justify a safe generic GNU-profile change from this bounded evidence.

CURRENT REFUSAL / HONEST LIMIT
validateCaptureRepetition currently rejects any referenced group nested inside
a repeat with maximum>1 whose child is classified nullable, including fixed
minimum repetitions, nested groups, and conservative nullable backreferences.
That is broader than the exact discovered '\(a*\)*\1' tuple. It can be an
explicit documented limitation while unresolved, but must stay in the original
native denominator as unsupported/different, never recategorized as parity.
Do not silently remove the native case, revise its expected bytes, or claim
general nullable-capture support. Root/author must decide GNU compatibility vs
normative semantics explicitly; this leaf did not change the contract.
