# WebDAV timestamps: capable fixture, explicit unsupported-provider control

Frozen base b2d202a7a2c8831df9c2d143bc43c74d1a099b14 already implements persistent conditional dead-property timestamps. The original MockDav returns 501 for PROPPATCH; original metadata-row failure is retained in 00-original-fixed-runner. Only this positive metadata row now uses the existing PropertyDav protocol fixture over the existing loopback transport. Other shared fixtures/expectations are unchanged. PropertyDav now decodes Uint8Array request bodies, as needed by that loopback fixture, instead of stringifying them into comma-separated integers. No product source changed.

Successful results: metadata row 1/1; new timestamp profile controls 8/8; existing timestamp backend tests 7/7. All zero skipped/cancelled/TODO. Positive assertions require exact persisted fractional/negative values, fresh-instance visibility, binary/namespace preservation, strong If-Match, one PROPPATCH and no PUT rewrite. Negative controls retain original HTTP501/typed ENOTSUP, property403/EACCES,423/EBUSY,424/EIO,507/ENOSPC, stale HTTP412/EAGAIN, and lost acknowledgement EIO with actual persisted prior effects. Error paths are asserted at the typed API boundary.

03-webdav is retained as an unsuccessful test-author iteration: loopback Uint8Array decoding was missing; two newly constructed clients omitted required injected fetch. Its raw results are not product regressions. The corrected fixture/client injection is independently replayed in this fresh phase. Before/after source hashes are stable.

Protocol: RFC4918 sections9.2/9.2.1 require PROPPATCH processing, recommend arbitrary dead properties, and specify property-level statuses within Multi-Status. HTTP207 alone is insufficient. The existing extension does not change protected DAV:getlastmodified. Primary reference inspected August26,2026: https://www.rfc-editor.org/rfc/rfc4918.html#section-9.2 . Fixture support is not a claim that every provider supports this extension.

Current adapter README explicitly defines timestamps:true as implemented extension, not successful provider negotiation. Shared contracts do not currently settle negotiated-vs-implemented capability semantics; root/Curie should clarify centrally, without inventing a new capability in this task. This correction does not weaken required support or skip a provider failure: the capable profile must succeed, the original unsupported profile must fail honestly and preserve state.
