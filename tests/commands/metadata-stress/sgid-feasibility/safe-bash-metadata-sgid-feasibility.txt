WHY COMMAND-ONLY CANDIDATES ARE UNSAFE OR INSUFFICIENT
1. Post-stat then return1 detects some missing SGID but leaves0707, not GNU's
   unchanged original. This fails all six required effects even if status matches.
2. Restore the original mode after detection overwrites a concurrent mode change
   or replacement/alias target; even a same dev/ino check is not atomic and ctime
   is irreversibly changed. Errors/cancellation may occur between each effect.
   Same identity is not permission authority, exclusion, or an incarnation lease.
3. Probe chmod(oldMode|SGID) then restore is itself a mutation, including possible
   ctime/SGID changes. Success/failure does not reserve target identity, group,
   credentials or ACL until the final operation. Not a harmless preflight.
4. Check process.platform/getuid/getgroups against FileStat.gid: metadata lacks
   backend credential authority and ACL context; optional gid may be absent;
   Memory/remote/wrappers use different namespaces/policies. Even a RealFS brand
   does not atomically bind a pathname to stat metadata/authorization. No such
   indiscriminate host lookup should be added to metadata.
5. Blanket SGID rejection, permissions:false downgrade, or ignoring EPERM would
   contradict positive native workflows and/or misreport missing/error cases.
6. Retrying on EPERM/EIO/transient failures duplicates effects or silently changes
   requested mode. Abort-bearing errno reasons are especially unsafe to swallow.
No candidate closes all six while honestly preserving raw RealFS and the safety
requirements through the current stat/lstat/chmod-only contract.

MINIMUM ROUTED REQUEST / PRECISE DESIGN BOUNDARY (NOT APPROVED API)
Root should ask Poincare/Curie whether an OPTIONAL backend-owned, effectful
permission operation can express selected GNU/Darwin fchmodat-style behavior,
without changing existing raw FileSystem.chmod semantics. Shape/name undecided;
do not publish a proposed export as delivered. Required behavior:
- Receives virtual path, already-calculated requested mode, supplied signal and
  an explicit supported permission-operation profile; does not import process
  identity or native paths into the command. Wrappers route to actual backend.
- Performs native permission authorization and application as one backend
  operation, with no userspace SGID-stripping retry; this host's SGID refusal is
  EPERM before permission effects. Ordinary, SGID-clear and legitimate SGID-set
  operations remain available. Existing raw chmod keeps current Node semantics.
- Prefer real fchmodat-equivalent host authority rather than an emulated group
  preflight. Separate metadata-only authorization without atomic enforcement
  is insufficient. A profile name must not promise all platforms retain every
  requested bit: the target is GNU's selected syscall status/effects, not an
  invented universal 'exact bits' guarantee.
- If snapshot-based checks are instead proposed, backend must bind/check all
  authorization-relevant state in the same operation, without a check/use gap;
  existing compareEntry/identityScope do not supply this. Path-resolution race
  limitations must be explicit, not upgraded to race-proof claims. A one-syscall
  native operation matches that syscall's race semantics, not a global lease.
- Preserve native denial/missing/readonly/transient/backend errors and aborts;
  no broad retries, rollback or fabricated success. Before-dispatch abort has
  no effect; in-flight host mutation may complete and cannot be retroactively
  cancelled. Document the exact completion/abort boundary.
- Missing capability/authority is explicit unsupported selected-profile work,
  not silently raw fallback or an acceptance waiver. Do not disable legitimate
  raw chmod/virtual metadata workflows merely to make a score green.
Current API exposes no such operation or atomic permission-authority facility.
Current Node-backed path uses public libc chmod. This investigation has not
identified a supported zero-dependency Node primitive bypassing that retry.
If root permits an explicitly host-injected backend primitive, the library can
remain zero-runtime-dependency; host implementation feasibility remains separate.
No native addon, subprocess/host command, eval, private Node binding or product
fallback is proposed as an implemented solution. If no backend primitive is
allowed/available, exact selected GNU compatibility remains blocked, not waived.
